Case Study · Personal Project

Capsule Shooter

A top-down wave shooter where every arena is procedurally generated — and always solvable.

Unreal Engine 5 C++ Procedural Generation Behavior Trees Data Tables Solo
Survive waves of capsule enemies in a top-down arena built fresh each level from a grid of tiles. The interesting problems here weren't the shooting — they were generating a map that's random but never traps the player, a spawn director that punishes camping without feeling unfair, and keeping a map generator, a spawn manager, a game mode and a HUD in sync without wiring them into a knot.
01 / Map Generation

Random obstacles that never wall the player in

The problem

Each level is an N × N grid of tiles, some fraction of which become obstacles. Placing obstacles at random is easy; the catch is that a random layout regularly seals off a pocket of the arena — or boxes the player's spawn in entirely — and an unreachable region is where enemies spawn that the player can never fight. The generator has to guarantee the whole floor stays connected.

The decision

Shuffle every tile with a Fisher–Yates pass, then walk the shuffled list as obstacle candidates. For each candidate: tentatively make it an obstacle, run a recursive flood fill from the centre tile, and count how many tiles it can reach. If that count equals (total − obstacles placed so far), the map is still fully connected and the obstacle stays; otherwise it's reverted and the tile goes back in the free pool. The centre tile is never eligible — that's the player's spawn. Obstacle colours are lerped across a per-level palette by grid position, so each arena reads as one piece.

Trade-off: a flood fill per accepted obstacle is O(tiles) each, so generation is roughly O(tiles²) — completely fine at these grid sizes, but it wouldn't scale to a large map. For that I'd switch to a union-find structure and check connectivity incrementally instead of re-flooding.
02 / Data-Driven Levels

A level is a row in a table, not a subclass

The problem

Every wave differs in grid size, obstacle density, which gun the player gets, how many enemies spawn, whether spawning is finite or endless, and how fast they arrive. Encoding that per-level in code means a recompile for every balance tweak and a new class per wave.

The decision

Levels are FLevelData rows in a data table (tile count, obstacle percent, gun class, enemies-per-wave, infinite-spawn flag, seconds between spawns), with colour schemes in a parallel FColourPalette table. The game instance reads the table once on Init, then owns the run state — current level, carried-over health, score — across the full level reload that happens between waves, advancing when a WaveEnded delegate fires.

03 / Anti-Camping Spawn Director

Standing still should stop being safe

The problem

In a wave shooter with ranged enemies, the dominant strategy is to find a corner with one approach angle and hold it. If enemies always spawn at random tiles, a camper is rewarded — the fight comes to them single-file.

The decision

The map generator polls the player's position on a timer. If the player hasn't moved more than one tile-length since the last check, it works out which tile they're standing on and broadcasts it; the spawn manager forces the next enemy to spawn on that tile instead of a random one. When the player is moving normally, spawns fall back to a random unoccupied tile. Either way the target tile pulses — a colour flash driven by chained short timers — for a visible telegraph window before the enemy actually appears, so a forced spawn is a warning, not an ambush.

Trade-off: "moved less than one tile" is a blunt check — a player strafing a tight circle reads as mobile. I kept it simple because the telegraph flash makes a wrong call cheap; a smarter version would track a movement heatmap over a few seconds.
04 / Decoupled Game Flow

Four managers that never hold hard references to each other

The problem

Map generation, enemy spawning, wave/score bookkeeping, and the HUD all have to react to each other: a spawn increments a counter, the last kill of a wave ends the level, the player dying stops spawning and shows a menu. If each system reaches directly into the others, the dependency graph becomes circular and nothing can be tested or changed in isolation.

The decision

Each manager registers itself with the game mode in its own BeginPlay; the game mode is the only thing that knows the full set. Everything after that is multicast delegates — PlayerDiedDelegate, SpawnedEnemyDelegate, EnemyDiedDelegate, WaveEnded, SpawnOnPlayerDelegate, StopEnemies — wired together with lambdas in one place. The map generator doesn't know the spawn manager exists; it just broadcasts "player is camping this tile" and something downstream handles it.

Trade-off: the wiring all lives in the game mode's StartLevel, which becomes a long function of lambda subscriptions. It's centralised and readable top-to-bottom, but it is the one place that knows everything — the cost of keeping every other system ignorant of its neighbours.
05 / Enemy Attack

A lunge that doesn't need a navmesh

The problem

Capsule enemies close and strike. Running the attack itself through navmesh pathfinding is overkill for a short lunge in an open arena, and it fights the readable, arcade feel — you want a clean dash in and a dash back out.

The decision

Behaviour runs on a Behavior Tree: a service continuously writes the enemy→player distance to the blackboard for range decorators, an attack-cooldown decorator gates re-entry, and the attack itself is a latent task that interpolates the enemy toward a point just short of the player (offset by the player's capsule width), applies damage on contact, then interpolates back to where it started before finishing. An IsAttacking blackboard bool keeps other branches from firing mid-lunge.

06 / Endless Mode Ramp

Making infinite waves actually escalate

The problem

An infinite-spawn level with a fixed spawn interval plateaus — after the first minute the difficulty never changes and the run just becomes a test of patience.

The decision

The game mode counts spawns in endless mode, and every fixed number of spawns it tells the spawn manager to shorten the interval. The pressure compounds on its own the longer the player survives, and the score they're chasing is the reward for riding the curve up.
