Case Study

Project Greenleaf

Designing the systems behind an RTS / grand-strategy hybrid — squads, campaigns, and everything between.

Unreal Engine 5.7 C++ Senior Programmer Nytwolf Games
This isn't a feature list. Greenleaf has a hex-map campaign layer feeding real-time large-scale battles, which means the design problems compound: the AI making province decisions has to hand off to the AI commanding squads on a battlefield, and the UI displaying both has to do it at 60fps. Every system below started as a constraint the hybrid genre imposes, and the interesting part was the decision — especially when Unreal had an existing framework that looked like it might fit but didn't.
01 / Squad Ability System

A purpose-built command queue, not GAS adapted to a squad

The problem

Unreal's Gameplay Ability System is built for character-scale abilities — one actor, one ability activating, costs deducted from an attribute set, a cooldown timer ticking down. An RTS squad command is structurally different. A player right-click must preempt an ongoing autonomous AI decision without argument. A mid-climb wall traversal must be non-interruptible — the squad cannot be redirected while soldiers are halfway up a wall segment. A "move to position" order may silently require three sequential legs — path to the wall, climb it, path the other side — but the player sees only "moving." GAS has no model for command source priority, non-interruptible traversal phases, or a chained multi-leg order that reads as a single command to every caller.

The decision

Pooling and reset.

One ability instance is allocated per ability type per squad and never destroyed. Between uses, the instance is wiped back to its default state by copying every reflected property from the class archetype in-place — a full reset without a heap allocation. The owning squad reference and cached game mode are excluded from this wipe and stay bound for the lifetime of the pool entry.

Order start flow.

Every incoming order passes through four sequential gates. First, priority: if the command didn't come from the player and a player order is already active, the command is rejected — the sole exception is the retreat ability, which a morale collapse can force even over a live player order. Second, restart: if the incoming type matches the ability already running, the live instance decides whether to accept or refuse the re-issue. The melee attack ability uses this to reject reissuance against the same target, keeping the chase timer running undisturbed. Third, lock: if the running primary or any active secondary leg has declared itself non-interruptible, the incoming order is held in a single pending slot and applied as soon as the lock clears. Fourth, teardown and commit: the old primary is interrupted, the secondary stack is cleared, listeners are notified, and the new ability is pulled from the pool and started.

Primary / secondary chain.

One ability is pinned as the primary for the entire lifetime of an order. Beneath it, a stack of secondary legs drains in sequence — each runs to completion before the next begins. A leg that fails terminates the whole order. When the stack empties, the primary decides what happens next. The default is to end with success. Abilities that need to keep running — the melee attack — override that callback as a no-op, letting the primary stay alive while it re-issues fresh movement legs on the next timer tick.

Melee chase loop.

The melee attack ability fires a repeating two-second timer. Each tick checks whether the target has moved beyond a threshold — 20% of current distance, clamped between 300 and 1500 units. If so, it recomputes the formation destination and issues a fresh movement chain, which becomes a new set of secondary legs beneath the pinned primary. The legs run and drain; because the completion callback is a no-op, the primary stays alive. The loop ends only on target death, timeout, or morale collapse. The caller sees one continuous attack order for however long the chase lasts.

Interrupt and resume.

A running ability can be interrupted and saved to a single-slot cache. A new ability starts immediately over it. To resume, the cached type is restarted with no parameters — a signal to the ability that it must regenerate its own state from whatever it stored internally, since the original parameters are gone. The cache holds only one entry; trying to interrupt an already-interrupted ability fails rather than nesting.

Combat suppression.

When a movement order is committed, the system decides whether it should block autonomous engagement. The rule: suppress if the incoming ability is not a combat ability, and either the command came from the player or the squad was already in a fight. When suppression is active, engagement processors ignore nearby enemies for the duration of the move — a squad given a withdrawal order passes through an enemy line without stopping to fight. The suppression clears when the move ends or a combat ability takes over.

Defend and engage-at-will.

The defend ability runs a periodic scan for approaching threats — enemies moving toward the squad above a configured angle threshold. On finding one, it issues a minimal formation adjustment to rotate the squad toward the threat without triggering a new engagement order. Actual combat is left to the engagement processors, which respect the squad's engage-at-will setting. The ability disables itself when engage-at-will is turned off and re-enables when it turns back on, so the scan never runs when it would have no effect.

Trade-off: no free attribute or cost framework — ability costs and cooldowns are wired manually against the squad's stat component (morale, fatigue, ammo). The reflection-based reset is thorough but costs more than a hand-written clear; for abilities with large state and high reset frequency, this is measurable. Those are the prices of squad-native semantics GAS can't express: command source priority, mid-chain locking, per-leg interruptibility, transparent chaining, and a chase loop that reads as a single order to everything above it.
02 / Dynamic UI Plugin

Data pushes to widgets, not widgets pulling from systems

The problem

Greenleaf's campaign UI is a living war-room dashboard: selecting an army must immediately surface all options for that army; a resource gain must appear in the top bar before the input call returns; switching from an owned province to an enemy one must swap every panel to the right context in the same frame. Before a shared solution existed, widgets were individually coupled to game systems. When a settlement's resource balance changed, the handler had to manually locate and call an update method on every widget that displayed that value. Widgets cached state locally, so stale data bugs were constant. Adding a new display element meant threading update logic through multiple code paths. There was no single source of truth — just a web of direct calls growing wider every sprint.

The decision

The plugin inverts the dependency. Game systems don't call into widgets — they call into data models, which are observable typed stores. Widgets declare which fields on which models they care about at construction time. When a handler writes a new value to a field, every widget bound to that field updates synchronously in the same call stack frame — before the handler returns, before the next line runs.

Observable data model.

Each domain (army, province, diplomacy, top bar) has its own data store holding a map of named fields to typed values. A field can carry an integer, float, string, texture, colour, boolean, or 2D vector — the value object stores whichever type was last written. Writing a field fires a multicast delegate immediately; there is no tick-based batching. A reentrance guard silently drops any write that arrives from inside a delegate callback, preventing circular update loops.

Field name registry.

Field names are string constants held in a central data asset, not literal strings scattered across the codebase. Both the handler setting a value and the widget binding to it reference the same property on the same asset. Renaming a field is a single-point change; a misspelled binding fails to connect at construction rather than silently diverging at runtime. The asset is loaded once and cached statically so every widget instance shares the same pointer.

Type-safe update dispatch.

When a field change arrives at a widget, a static dispatch table maps the concrete type of the bound component to the right update call — a text block gets its text set, a progress bar gets its percentage set, an image gets its brush or colour updated. The table is built once and reused. Adding support for a new component type means adding one entry to the table; the widget base class and all existing bindings are untouched.

Handler bridge and exclusive context.

Handlers are the only code that touches models directly. They are owned by the player state and activated or deactivated by the player state machine. Only one handler is ever active per context — switching from an own army to an enemy army calls the previous handler's teardown before the new one initialises, so two handlers never write to the same model simultaneously. Handlers never touch widgets; they only call into models. Widgets never touch game systems; they only observe models.

Trade-off: synchronous updates mean there is no batching — a handler that writes ten fields fires ten broadcasts, each updating all bound widgets before the next write runs. This is the primary UI CPU cost at campaign scale, where frequently updated fields like resource counts have several listeners each. The string-based field registry also has no compile-time validation; a misspelled field name silently binds to nothing rather than producing a build error. Both are accepted costs: the synchronous model is what makes the war-room responsiveness feel possible, and the asset-based registry keeps field definitions decoupled from code compilation so designers can add new fields without touching a header file.
03 / Battle Performance

Frustum culling, parallelisation, and frame-spreading across the soldier simulation

The problem

A large-scale battle runs hundreds of Mass Entity soldiers simultaneously. Several per-frame costs were accumulating: transform sync (position, rotation, ground alignment, charge VFX) ran for every soldier regardless of camera visibility; animation state classification and state transition calls ran serially on the game thread; the spatial grid rebuilt its cell occupancy list every frame with redundant allocation; formation anchor positions recomputed for all squads on the same frame; and the vertex animation batch update had no LOD-based throttling. Each of these was cheap in isolation — at hundreds of soldiers, ticking in the same frame window, they compounded.

The decision

The work was addressed in layers, each targeting a different bottleneck:

Frustum culling + distance-banded frame skipping.

A utility tests whether a world location is inside the camera frustum, returning depth alongside the boolean. Transform sync was moved into a dedicated batch processor that gates on two layers: units outside the frustum are skipped entirely; in-frustum units are placed into distance bands — near (0–10k, every frame), mid (10k–25k, every 3 frames), far (25k+, every 5 frames). A modulo stagger spreads far-range updates across frames rather than bursting them on the same tick. The transform sync and ragdoll sync steps were both moved to PostPhysics so they read ground-snapped transforms from the current frame rather than one frame stale.

Ground alignment as a parallel processor.

Ground alignment (terrain raycast snap) was extracted from the render sync loop into its own processor, which runs in parallel across all entity chunks in PostPhysics, after overlap resolve and wall processors. A cached last position skips the trace entirely when a unit's horizontal position hasn't moved more than 1 unit since the last snap — terrain is static, so a unit standing still never needs to retrace.

Animation state classification across chunks in parallel.

Animation classification previously ran in parallel within a single chunk, writing results to staging fields on the render data fragment, then consuming them in a serial state transition pass — chunks were still processed one at a time. This was replaced so that classification and state transitions run across all chunks simultaneously, keeping results as stack locals rather than writing to shared fragment fields. The intermediate staging fields were deleted from the fragment entirely. The blocker for true parallelism was that state transitions made game-thread-only calls (timer registration and state change broadcasts); these were deferred to the game thread asynchronously with weak-pointer guards, making the transition logic safe to call from any worker thread.

Spatial grid cell insertion parallelised.

The spatial grid's cell population loop was switched to run in parallel across entity chunks. Cell writes are guarded by a per-cell lock (one lock per cell, allocated once at grid initialisation), so parallel chunk workers never contend on the same cell entry. Redundant cell clearing was also removed — the grid's own rebuild already zeroed cells — and a count array was promoted to a member to eliminate a heap allocation every frame.

Formation anchor computation staggered per squad.

Formation anchor positions previously recomputed for all squads on a fixed timer, dumping the full work onto the game thread simultaneously every 0.1s. This was replaced with per-squad staggering using each squad's entity identity as an offset into a 6-frame cycle. Each squad still recomputes at roughly 10Hz, but the identity-based offset distributes which frame in the cycle belongs to each squad — the game thread gets a steady drip instead of a burst.

Vertex animation LOD frame-skipping.

The vertex animation batch update already ran via parallel iteration. LOD tier 2 components now skip every other frame; tier 3 skip three out of four frames. The stagger uses each component's index within the batch as an offset — a bare frame counter would burst all distant components on the same frame. A time accumulator continues to advance on skipped frames so the configured update rate is preserved when the call does run.

Trade-off: two correctness issues emerged from skipping work. First, soldiers reaching a wall-climb transition while outside the frustum never had their actor snapped to the wall top — fixed with a dedicated narrow processor that handles the one-frame transition snap unconditionally, outside the frustum gate. Second, deferring state change broadcasts asynchronously introduces a one-frame lag on delivery — imperceptible at animation state granularity, where idle/run transitions have no frame-exact requirement. The pattern throughout is the same: keep the hot path fast, isolate correctness edge cases into their own narrow processors rather than adding branches to the common path.
