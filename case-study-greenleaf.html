Case Study

Project Greenleaf

Designing the systems behind an RTS / grand-strategy hybrid — squads, campaigns, and everything between.

Unreal Engine 5.7 C++ Senior Programmer Nytwolf Games
This isn't a feature list. Greenleaf has a hex-map campaign layer feeding real-time large-scale battles, which means the design problems compound: the AI making province decisions has to hand off to the AI commanding squads on a battlefield, and the UI displaying both has to do it at 60fps. Every system below started as a constraint the hybrid genre imposes, and the interesting part was the decision — especially when Unreal had an existing framework that looked like it might fit but didn't.
01 / Squad Ability System

A purpose-built command queue, not GAS adapted to a squad

The problem

Unreal's Gameplay Ability System is built for character-scale abilities — one actor, one ability activating, costs deducted from an attribute set, a cooldown timer ticking down. An RTS squad command is structurally different. A player right-click must preempt an ongoing autonomous AI decision without argument. A mid-climb wall traversal must be non-interruptible — the squad cannot be redirected while soldiers are halfway up a wall segment. A "move to position" order may silently require three legs in sequence — path to the wall, climb it, path the other side — but the player sees only "moving." GAS has no model for command source priority, non-interruptible traversal phases, or a chained multi-leg order that reads as a single command to every caller.

The decision

Built USquadAbility — pooled UObject instances (one per ability class per squad), initialized once, reset via CDO copy between uses. USquadAbilityComponent keeps a pinned CurrentPrimaryAbility for the lifetime of an order, and drains a SecondaryActiveStack of chain legs beneath it. ECommandSource (Player > AI > Autonomous) gives player orders absolute preemptive priority — a non-player command is silently rejected while a player order is active, with the single exception of morale-driven auto-retreat, which always gets through. CanOverride() lets any leg declare itself non-interruptible; incoming orders queue into PendingPrimaryAbility and auto-apply when the lock clears. The entire climb sequence — move, climb, move — reads as one order to the squad AI and to the player.

Trade-off: no free attribute/cost framework — ability costs and cooldowns are wired manually against USquadStatsComponent (morale, fatigue, ammo). That's the price of squad-native semantics GAS can't express: command source priority, mid-chain locking, and transparent leg chaining under a single player-facing order. For a single-character RPG, GAS would have been the right call. For a squad commanding hundreds of units across a battlefield, it would have been the wrong abstraction from day one.
02 / Battle Performance

Frustum culling, parallelisation, and frame-spreading across the soldier simulation

The problem

A large-scale battle runs hundreds of Mass Entity soldiers simultaneously. Several per-frame costs were accumulating: transform sync (position, rotation, ground alignment, charge VFX) ran for every soldier regardless of camera visibility; animation state classification and EnterState calls ran serially on the game thread; the spatial grid rebuilt its cell occupancy list every frame with redundant allocation; formation anchor positions recomputed all squads on the same frame; and the vertex animation batch update had no LOD-based throttling. Each of these was cheap in isolation — at hundreds of soldiers, ticking in the same frame window, they compounded.

The decision

The work was addressed in layers, each targeting a different bottleneck:

Frustum culling + distance-banded frame skipping.

Built UFrustumFunctionsLibrary to test whether a world location is inside the camera frustum, returning Z depth alongside the boolean. Transform sync was moved into a dedicated UBatchSyncProcessor that gates on two layers: units outside the frustum are skipped entirely; in-frustum units are placed into distance bands — near (0–10k, every frame), mid (10k–25k, every 3 frames), far (25k+, every 5 frames). A unit updates only when GFrameCounter % FrameInterval == LastFrameProcessed % FrameInterval. The modulo stagger spreads far-range updates across frames rather than bursting them on the same tick. UBatchSyncProcessor and UUnitRagdollSyncProcessor were moved to PostPhysics so they read ground-snapped transforms from the current frame rather than one frame stale.

Ground alignment as a parallel processor.

Ground alignment (terrain raycast snap) was extracted from the render sync loop into UUnitMovementGroundAlignProcessor, which runs via ParallelForEachEntityChunk in PostPhysics after overlap resolve and wall processors. A position cache (LastGroundAlignLocation) skips the trace entirely when a unit's XY hasn't moved more than 1 unit since the last snap — terrain is static, so a unit standing still never needs to retrace.

Animation state classification across chunks in parallel.

Animation classification previously used ParallelFor within a single chunk, writing results to staging fields on FUnitRenderFragment (PendingAnimState, bPendingIsChargedAttack, etc.), then consuming them in a serial EnterState pass. Chunks were still processed one at a time. Replaced with Query.ParallelForEachEntityChunk — classification and EnterState now run across all chunks simultaneously, with results kept as stack locals. The five staging fields were deleted from the fragment entirely. The blocker for true parallelism was game-thread-only calls inside EnterState (timer registration, AnimationStateChanged broadcast); these were wrapped in AsyncTask(ENamedThreads::GameThread) with weak-pointer guards, making EnterState safe to call from any worker thread.

Spatial grid cell insertion parallelised.

The spatial grid's cell population loop was switched from ForEachEntityChunk to ParallelForEachEntityChunk. Cell writes are now guarded by a per-cell FCriticalSection (one lock per cell, allocated at InitGrid time), so parallel chunk workers never contend on the same cell entry. Redundant cell clearing was also removed — the grid's own rebuild already zeroed cells — and CellCounts was promoted to a member to eliminate a heap allocation every frame.

Formation anchor computation staggered per squad.

Formation anchor positions previously recomputed for all squads at a fixed UpdateInterval timer, which dumped the full work onto the game thread simultaneously every 0.1s. Replaced with per-squad staggering: (GFrameCounter + Entity.AsNumber()) % 6 != 0 → skip. Each squad still recomputes at ~10Hz, but the entity handle distributes which frame in the cycle is each squad's turn — the game-thread queue gets a steady drip instead of a burst.

Vertex animation LOD frame-skipping.

VAWorldSubsystem::BatchUpdateTransforms already ran via ParallelFor. LOD tier 2 components now skip every other frame; tier 3 skip three out of four frames. The stagger uses (GFrameCounter + ComponentIndex) & mask — a bare frame counter would burst all tier-2/3 components on the same frame. AdvanceLODAccumulator(DeltaTime) keeps the LOD time accumulator ticking on skipped frames so the configured update rate is preserved when the call does run.

Trade-off: two correctness issues emerged from skipping work. First, soldiers reaching wall-climb transition while outside the frustum never had their actor snapped to the wall top — fixed with UWallTransitionResolveProcessor, a narrow PostPhysics processor that handles the one-frame transition snap unconditionally. Second, deferring AnimationStateChanged via AsyncTask introduces a one-frame lag on broadcast delivery — imperceptible at animation state granularity, where idle/run transitions have no frame-exact requirement. The pattern throughout is the same: keep the hot path fast, isolate correctness edge cases into their own narrow processors rather than adding branches to the common path.
