Case Study

Project Greenleaf

Designing the systems behind an RTS / grand-strategy hybrid — squads, campaigns, and everything between.

Unreal Engine 5.7 C++ Senior Programmer Nytwolf Games
This isn't a feature list. Greenleaf has a hex-map campaign layer feeding real-time large-scale battles, which means the design problems compound: the AI making province decisions has to hand off to the AI commanding squads on a battlefield, and the UI displaying both has to do it at 60fps. Every system below started as a constraint the hybrid genre imposes, and the interesting part was the decision — especially when Unreal had an existing framework that looked like it might fit but didn't.
01 / Squad Ability System

A purpose-built command queue, not GAS adapted to a squad

The problem

Unreal's Gameplay Ability System is built for character-scale abilities — one actor, one ability activating, costs deducted from an attribute set, a cooldown timer ticking down. An RTS squad command is structurally different. A player right-click must preempt an ongoing autonomous AI decision without argument. A mid-climb wall traversal must be non-interruptible — the squad cannot be redirected while soldiers are halfway up a wall segment. A "move to position" order may silently require three sequential legs — path to the wall, climb it, path the other side — but the player sees only "moving." GAS has no model for command source priority, non-interruptible traversal phases, or a chained multi-leg order that reads as a single command to every caller.

The decision

Pooling and reset.

USquadAbility instances are allocated once per ability class per squad and never destroyed. Between uses, ResetAbility() restores the instance to its CDO defaults by iterating every reflected property and copying from the class default object in-place — a full state wipe without a heap allocation. Two properties are excluded from the reset: the owning Squad pointer and the cached GameMode reference, which stay bound for the lifetime of the pool entry.

StartAbility flow.

Every incoming order passes through four sequential gates before it runs. First, priority: if the source is not Player and a player order is already active, the command is rejected — the sole exception is URetreatSquadAbility, which a morale collapse can trigger autonomously even over a live player order. Second, restart: if the incoming ability class matches the current primary, HandleRestart() is called on the live instance; returning false aborts the start without disrupting the running order. In practice, UMeleeAttackSquadAbility uses this to reject reissuance against the same target — the chase timer keeps running undisturbed. Third, lock: if CanOverride() returns false on either the primary or the active secondary leg, the incoming order is deferred into PendingPrimaryAbility (last-write wins) and applied as soon as the lock clears. Fourth, teardown and commit: the old primary receives EndAbility(Interrupted), the secondary stack is drained, OnCommandOver broadcasts, and the new ability is fetched from the pool, set as CurrentPrimaryAbility, and started.

Primary / secondary chain.

USquadAbilityComponent keeps a pinned CurrentPrimaryAbility for the entire lifetime of an order and drains a SecondaryActiveStack of legs beneath it. When a primary issues a chain — a move that crosses terrain requiring a climb — it calls StartSecondaryStack(legs); the component pops and starts each leg in turn as CurrentSecondaryAbility. A leg that ends with Success advances to the next; a leg that ends with Fail terminates the whole order. When the stack empties, CurrentPrimaryAbility->OnSecondaryStackComplete() is called. The default implementation ends the primary with Success. Abilities that need to keep running — like UMeleeAttackSquadAbility — override it as a no-op, letting the primary stay alive while the chase timer re-issues fresh movement legs on the next tick.

Melee chase loop.

UMeleeAttackSquadAbility fires a repeating two-second timer. Each tick measures whether the target has moved beyond a threshold (20% of current distance, clamped 300–1500 units). If so, it recomputes the formation destination and issues a fresh Move_Chain() — which feeds a new set of nav legs into StartSecondaryStack(). The leg runs and completes; since OnSecondaryStackComplete() is a no-op, the primary stays pinned. Two seconds later the timer fires again. The loop ends only when the ability explicitly calls EndAbility() — on target death, timeout, or morale collapse. The caller sees one continuous "attack" order for as long as the chase lasts.

Interrupt and resume.

PushInterruptAndStart() caches the current primary's class into InterruptCache (params are intentionally left empty) and immediately starts a new ability over it. ResumeInterruptedAbility() restores the cached class and calls StartAbility() with empty params, signalling the ability to regenerate its own state from stored fields. The pattern assumes the interrupted ability has kept enough state to restart itself — it cannot rely on the original call-site params being present. The cache holds a single slot; trying to interrupt an already-interrupted ability returns false rather than nesting further.

Combat suppression.

When a move order is committed, ComputeSuppressesCombat() decides whether it should block autonomous engagement: suppress if the incoming ability is not a combat ability, and either the source is Player or the squad was already engaged. If suppression applies, bMoveSuppressCombat is set on the squad's ECS state fragment. Engagement processors check this flag before initiating new fights — a squad given a move order retreats through a line of enemies without stopping to attack them. The flag clears when the move order ends or a combat ability is started.

Defend and engage-at-will.

UDefendSquadAbility runs a periodic scan for approaching threats — enemies moving toward the squad with a dot product above a configured threshold. On finding one, it issues a trivial formation move a few centimetres perpendicular to the threat vector, rotating the squad in place without triggering a new engagement order. Actual combat is left to the engagement processors which respect the squad's bIsEngageAtWill flag. The ability is disabled and re-enabled as engage-at-will toggles, so the scan never runs when it would have no effect.

Trade-off: no free attribute/cost framework — ability costs and cooldowns are wired manually against USquadStatsComponent (morale, fatigue, ammo). The CDO-copy reset is thorough but reflection-based, which costs more than a hand-written clear; for abilities with large property sets that reset frequently, this is measurable. Those are the prices of squad-native semantics GAS can't express: command source priority, mid-chain locking, per-leg interruptibility, transparent chaining, and a chase loop that reads as a single order to everything above it.
02 / Battle Performance

Frustum culling, parallelisation, and frame-spreading across the soldier simulation

The problem

A large-scale battle runs hundreds of Mass Entity soldiers simultaneously. Several per-frame costs were accumulating: transform sync (position, rotation, ground alignment, charge VFX) ran for every soldier regardless of camera visibility; animation state classification and EnterState calls ran serially on the game thread; the spatial grid rebuilt its cell occupancy list every frame with redundant allocation; formation anchor positions recomputed all squads on the same frame; and the vertex animation batch update had no LOD-based throttling. Each of these was cheap in isolation — at hundreds of soldiers, ticking in the same frame window, they compounded.

The decision

The work was addressed in layers, each targeting a different bottleneck:

Frustum culling + distance-banded frame skipping.

Built UFrustumFunctionsLibrary to test whether a world location is inside the camera frustum, returning Z depth alongside the boolean. Transform sync was moved into a dedicated UBatchSyncProcessor that gates on two layers: units outside the frustum are skipped entirely; in-frustum units are placed into distance bands — near (0–10k, every frame), mid (10k–25k, every 3 frames), far (25k+, every 5 frames). A unit updates only when GFrameCounter % FrameInterval == LastFrameProcessed % FrameInterval. The modulo stagger spreads far-range updates across frames rather than bursting them on the same tick. UBatchSyncProcessor and UUnitRagdollSyncProcessor were moved to PostPhysics so they read ground-snapped transforms from the current frame rather than one frame stale.

Ground alignment as a parallel processor.

Ground alignment (terrain raycast snap) was extracted from the render sync loop into UUnitMovementGroundAlignProcessor, which runs via ParallelForEachEntityChunk in PostPhysics after overlap resolve and wall processors. A position cache (LastGroundAlignLocation) skips the trace entirely when a unit's XY hasn't moved more than 1 unit since the last snap — terrain is static, so a unit standing still never needs to retrace.

Animation state classification across chunks in parallel.

Animation classification previously used ParallelFor within a single chunk, writing results to staging fields on FUnitRenderFragment (PendingAnimState, bPendingIsChargedAttack, etc.), then consuming them in a serial EnterState pass. Chunks were still processed one at a time. Replaced with Query.ParallelForEachEntityChunk — classification and EnterState now run across all chunks simultaneously, with results kept as stack locals. The five staging fields were deleted from the fragment entirely. The blocker for true parallelism was game-thread-only calls inside EnterState (timer registration, AnimationStateChanged broadcast); these were wrapped in AsyncTask(ENamedThreads::GameThread) with weak-pointer guards, making EnterState safe to call from any worker thread.

Spatial grid cell insertion parallelised.

The spatial grid's cell population loop was switched from ForEachEntityChunk to ParallelForEachEntityChunk. Cell writes are now guarded by a per-cell FCriticalSection (one lock per cell, allocated at InitGrid time), so parallel chunk workers never contend on the same cell entry. Redundant cell clearing was also removed — the grid's own rebuild already zeroed cells — and CellCounts was promoted to a member to eliminate a heap allocation every frame.

Formation anchor computation staggered per squad.

Formation anchor positions previously recomputed for all squads at a fixed UpdateInterval timer, which dumped the full work onto the game thread simultaneously every 0.1s. Replaced with per-squad staggering: (GFrameCounter + Entity.AsNumber()) % 6 != 0 → skip. Each squad still recomputes at ~10Hz, but the entity handle distributes which frame in the cycle is each squad's turn — the game-thread queue gets a steady drip instead of a burst.

Vertex animation LOD frame-skipping.

VAWorldSubsystem::BatchUpdateTransforms already ran via ParallelFor. LOD tier 2 components now skip every other frame; tier 3 skip three out of four frames. The stagger uses (GFrameCounter + ComponentIndex) & mask — a bare frame counter would burst all tier-2/3 components on the same frame. AdvanceLODAccumulator(DeltaTime) keeps the LOD time accumulator ticking on skipped frames so the configured update rate is preserved when the call does run.

Trade-off: two correctness issues emerged from skipping work. First, soldiers reaching wall-climb transition while outside the frustum never had their actor snapped to the wall top — fixed with UWallTransitionResolveProcessor, a narrow PostPhysics processor that handles the one-frame transition snap unconditionally. Second, deferring AnimationStateChanged via AsyncTask introduces a one-frame lag on broadcast delivery — imperceptible at animation state granularity, where idle/run transitions have no frame-exact requirement. The pattern throughout is the same: keep the hot path fast, isolate correctness edge cases into their own narrow processors rather than adding branches to the common path.
