Case Study · Personal Project

Shimura Duel

Rebuilding the Lord Shimura duel from Ghost of Tsushima in Unreal — a study in melee feel and boss AI.

Unreal Engine 5.5 C++ Gameplay State Tree Motion Warping Solo
A single fight, replicated as faithfully as I could: attack, block, dodge, parry, posture, unblockable stances, and a boss that reads how you play and punishes it. This write-up is about the problems the fight forced on me — shared action logic between player and boss, attack data that has to travel with an animation, an aggression-tracking parry, and a state tree that kept deadlocking whenever the real world interfered with it — and how each one got solved.
01 / Shared Combat Base

One action state machine for both the player and the boss

The problem

Shimura and the player share almost the same move set — attack, block, dodge, parry — plus the reactive states around it (get-hit, dead). Writing that twice, once for a player-controlled character and once for an AI one, means every timing tweak or new interaction has to be made in two places and kept in sync. It also makes the fight fragile: if a dodge can be started one frame into a get-hit reaction on one character but not the other, that inconsistency is a bug the player will find.

The decision

Everything common lives on an ACombatCharacter base class, with ALordShimura and AShimuraPlayer deriving from it and the Blueprint classes built on top of those. A single EActionState enum (None / Attack / Dodge / Block / Parry / GetHit / Dead) is the source of truth. The states are deliberately mostly mutually exclusive — while one is active, the others are refused with a guard at the top of each action (if (CurrentState != None) return;). Health and posture are pulled out into an AttributeComponent shared by both.

The result is that "can I act right now" has one answer for both fighters, and the differences that should exist — the player picks a dodge direction from input, Shimura always dodges backward — are small overrides on top of shared code rather than parallel implementations.

Trade-off: a flat exclusive-state enum can't express layered states (blocking while repositioning, for instance). I accepted that because this is a one-on-one sword fight with a shallow verb set — no action needs a sub-action — and the guarantee that transitions are clean was worth more than the flexibility.
02 / Attack Data

Every attack's stats have to travel with its animation

The problem

When a katana connects, the game needs to know a lot about the specific swing that landed: how much health damage it deals, how much posture damage, whether it can be blocked at all (unblockable stance attacks can't), where its parry window sits, and which frame produces the impact — the camera shake and time dilation. That information is per-animation, not per-character, and hard-coding it into the attack code means it drifts out of sync the moment an animation is swapped or retimed.

The decision

Each attack animation gets a matching FAnimationInfo row (damage, stagger damage, defensible yes/no) and they're stored in a map keyed by the UAnimationAsset* itself. At the moment of a hit, the code walks the active montage's slot tracks and segments to find which animation is playing at the current playback position, then looks up its stats. That same lookup is how the game knows an unblockable attack has connected — the bIsDefendable flag comes straight off the animation that hit.

The two timing-sensitive windows are marked directly on the animation with anim notifies rather than stored as numbers: a become-parriable → start-swing range for when a parry is possible, and a start-impact → finish-swing range for when a landed hit triggers the camera shake. Distance-closing attacks use Motion Warping to lerp Shimura onto the target so the gap-closer lands cleanly instead of whiffing or overshooting.

Trade-off: resolving the current animation by scanning montage segments every hit is more work than passing an ID through the attack call — but it means the animation is the single place attack data lives, and designers retime windows by dragging notifies, never by editing code.
03 / Punishing Aggression

The boss should read how greedy you're playing

The problem

A boss that only reacts to individual attacks is trivially beaten by mashing. Shimura needed to notice a pattern — a player who never stops swinging — and answer it, without that turning into a hard-coded "parry every third hit" that players memorise in a minute.

The decision

Shimura tracks the time between the end of a player attack that landed and the start of the next one — effectively, how long the player waited before being greedy again. He keeps a short rolling window of those intervals, and when their average drops below a quarter of a second, he schedules a parry: he binds to the player's "attack is now parriable" delegate so the counter fires exactly in the window. Landing that parry puts the player into a three-second state where they can't block or dodge — a real opening for Shimura to punish — after which the tracking resets and the pressure has to build up again.

Trade-off: a rolling average over a handful of samples is coarse — a player can bait it. I kept it deliberately simple because the goal was a readable "stop mashing" signal, not an unbeatable read, and a system the player can learn to play around is the right amount of counterplay for a duel.
04 / State Tree Deadlocks

The hardest bug: the world interfering with the boss's plan

The problem

Shimura's behaviour runs on a Gameplay State Tree: strafe around the player; if they're far, use the Wind stance to close distance; if they're close, roll weighted-randomly between the unblockable Stone stance and the readable Water stance, leaning toward Water; if the player parries or dodges, drop into a Parry state and wait it out. The problem is that a state tree task that plays an attack and waits for the montage to end has no natural way to handle the montage being interrupted. If the player parries Shimura mid-swing, or lands a hit before his attack connects, the montage is cut short, the "wait for montage end" never completes, and the task hangs forever — the whole tree stops progressing.

The decision

Every way an action can terminate now fires a delegate. The attack task doesn't just wait for the montage to finish — it also binds to an OnAttackFinished delegate that carries how it ended (Success, GetHit, Parried). Getting hit or getting parried mid-attack broadcasts that delegate, the waiting task exits down the right transition, and the tree keeps moving. The parry and dodge tasks use the same pattern — bind to the outcome, not just the montage.

Trade-off: this is delegate plumbing the State Tree editor doesn't show you — the graph looks simpler than the fight actually is. I'd rather have that hidden wiring than model every interrupt as an explicit branch in the tree, which would have made it unreadable. If I rebuilt it I'd look at State Tree's transition events to pull more of it back into the asset.
05 / Where It Would Go Next

Known limitations and the extensions that fix them

What's rough right now

Stance attacks don't blend into each other — each stance has its own attacks but they read as separate swings, not combos. Shimura only ever dodges straight back. And parries depend entirely on timing rather than the swords physically meeting, because there's a single parry animation and no runtime control over the pose.

The planned fixes

Combos: map each attack animation to an array of animations that are allowed to follow it, so a quick follow-up input picks a valid continuation keyed on what just played — smooth chains instead of disconnected hits. Directional counters: give Shimura left/right dodges with a counterattack out of each, the way the player already can, so spacing him becomes a real problem. Control-rig parries: drive the parry pose with a control rig so the blade actually intercepts the incoming sword, instead of selling the block through timing and a canned animation.
