Case Study

Indian Special Forces

Designing the systems behind a top-down tactical squad shooter — solo, end-to-end.

Unreal Engine 5.5 C++ Solo Developer Neosphere Interactive
This isn't a feature list. Every system below started as a design problem the genre forces on you — imperfect information, squad-scale control, AI that has to feel different per archetype without becoming five hand-written brains — and the interesting part was the decision, not the typing. Where there was a simpler or more obvious approach I didn't take, I've called it out.
01 / Command & Control

One state machine, not five buttons doing five things

The problem

A squad-tactics game needs a lot of context-sensitive verbs — move, shoot, melee, heal, repair, toss a grenade, mount a vehicle — issued at a cursor position, on a selection that can range from one soldier to a full squad in formation. Wiring each verb straight to an input event gets unmanageable fast: the cursor icon, the UI highlight, and the actual order all have to agree on "what mode am I in right now," and duplicating that logic per-action is where bugs live.

The decision

AISF_CameraPlayerController tracks a single EControllerState enum as the source of truth for player intent (Move / PrimaryFire / TossGrenade / Melee / Heal / Repair / EnterExit…). Every action is a SetStateToX() / ShowXOption() pair — entering a state drives cursor feedback and valid-target highlighting, and a left-click just asks "what does the current state do with this click." Squad movement layers formation math (column, wedge, line, staggered column) on top of the same click point, and marquee/shift-select feed the same ChosenSoldiers array every state reads from.

Trade-off: a flat enum state machine is simpler to reason about than a full HFSM but doesn't compose sub-states — I accepted that because the action set is shallow (no state needs a state), and it kept the whole command layer legible enough to extend solo without a framework.
02 / Stealth & Fog of War

Imperfect information has to be readable, not just correct

The problem

The core loop is stealth: the player should only know what their soldiers can see, and enemies should only react to what they actually perceive — not have omniscient awareness of the player squad. Getting the simulation "correct" (raycasts, senses) is the easy half. The hard half is making that invisible information legible — a player who can't tell why an enemy noticed them just feels cheated.

The decision

Rather than write vision/detection from scratch, I built on top of proven systems — the FogOfWar plugin for per-unit vision reveal, and UAIPerceptionComponent (sight + hearing) for enemy awareness — and spent my own engineering budget on the layer that was actually missing: making it visible. UISF_VisionConeIndicatorComponent renders each enemy's live sight cone to the player, and ISF_WeaponRangeUIComponent / ISF_WeaponRadiusIndicator do the same for engagement ranges. A depletable night-vision resource (timed, UI-tracked) turns "can I see" into a tactical decision rather than a toggle.

Trade-off: I deliberately didn't reinvent vision-cone math or a custom perception stack — reusing battle-tested plugins for the simulation and putting original work into player-facing legibility was the higher-leverage choice for a solo dev on a fixed timeline.
03 / Enemy AI

Composable behavior instead of five hand-written brains

The problem

Three enemy archetypes (rifleman, machine gunner, sniper) each need distinct combat and patrol behavior. The naive path — a Behavior Tree or C++ state machine per archetype — means every shared behavior (find a target, reload when empty, follow a patrol route) gets re-authored three times, and tuning one enemy's timing risks silently drifting from the others.

The decision

I built enemy brains on UE5's GameplayStateTree instead of Behavior Trees, and split the logic into small, reusable building blocks: Evaluators that answer yes/no questions (STE_IsWeaponEmpty, STE_IsCombatTargetDead, STE_GetCombatTarget) and Tasks that do one thing (STT_ShootTarget, STT_Reload). Each archetype's tree is then composed from these shared pieces plus its own patrol-route evaluator, rather than duplicating logic. Cover-seeking works the same way at the query level: UISF_CoverTraceEnvQueryTest is a custom EQS test that scores candidate points against a threat context, so cover is discovered dynamically from level geometry instead of requiring hand-placed cover markers on every map.

Trade-off: StateTree's data-oriented composition costs more upfront design than a quick Behavior Tree per enemy — I judged it worth it because it meant new archetypes reuse existing tuned building blocks instead of growing the bug surface linearly with enemy variety.
04 / Combat & Weapons

One damage contract for soldiers, enemies, and trucks

The problem

Multiple weapon types (hitscan, projectile, grenades, rockets, melee) need to be fired, reloaded, and switched by both player-controlled and AI-controlled characters — and the things that can be hit range from a soldier, to an enemy, to a vehicle that should be repairable instead of killable. Coupling "how combat works" to a specific character class was going to force duplicate fire/reload logic between player and AI, and duplicate damage logic between characters and vehicles.

The decision

Combat logic lives in UISF_CombatComponent, an ActorComponent attached to any character — player soldier or AI enemy — so firing, reloading, and weapon switching are written once and driven by either a player click or an AI Task. Weapons share a common AISF_GunMaster base with ISF_HitscanGun and ISF_ProjectileGun subclasses. On the receiving end, damage/interaction is expressed as interfaces — ISF_InjurableInterface, ISF_HealableInterface, ISF_ExplodableInterface, ISF_RepairableInterface — so a truck implements "repairable, not injurable" and a soldier implements the opposite, without either one caring what concrete class is on the other end of a hit.

Trade-off: interfaces add a layer of indirection versus a single shared "Damageable" base class — I chose interfaces specifically so a vehicle could opt into repair semantics and opt out of injury semantics independently, which a single inheritance line couldn't express cleanly.
05 / Persistence & Objectives

Save data owned by the system that produces it

The problem

Mid-mission save/load in a systemic tactics game is a classic trap: soldier health and ammo, vehicle position and patrol progress, camera state, night-vision remaining, objective progress — if all of that gets funneled into one "level save" blob assembled by a god object, every new system means editing that one fragile aggregator, and save/load drift becomes a constant bug source.

The decision

Each subsystem owns its own serialization contract: SaveCombatData() /LoadCombatData() on the combat component, SaveControllerData()/LoadControllerData() on the player controller, and equivalents for soldiers, trucks, and the pilot — each returning a small typed struct (FCombatData, FTruckData, FControllerData…). ISF_LevelSaveGame just aggregates structs it doesn't need to understand. Mission objectives follow the same separation-of-concerns idea one level up: UISF_ObjectivesSubsystem loads objective definitions from data tables (designer-editable, no recompile) and keeps objective progress as separate runtime/save state.

Trade-off: more structs and more save/load functions to maintain than one big blob — but each one is small, owned, and testable in isolation, and adding a new saveable system never means touching code outside that system.
