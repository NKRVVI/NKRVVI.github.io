Combat System

A C++-only sandbox for third-person melee — hit reactions, enemy AI, and group aggro, built to experiment.

Unreal Engine 5 C++ only Motion Warping Pawn Sensing Solo
This one is honestly a testbed — an unfinished experiment in melee combat mechanics written entirely in C++, no Blueprint logic. The point wasn't to ship a game; it was to build the systems a souls-like needs and see where they strain. Below are the problems that actually took thought: sharing combat code between a player and an AI, an enemy state machine that doesn't stutter at range boundaries, a squad that alarms together, and attacks that don't whiff.
01 / Shared Combat Base

The player and the enemy are the same fighter underneath

The problem

A player character and an AI enemy in a melee game do almost the same things — equip a weapon, swing it, take a hit, react, die — but they're driven completely differently, one by input and one by a controller. Writing the combat twice means every timing change or new weapon interaction has to land in both places, and they drift.

The decision

An abstract ABaseCharacter that implements a IHitInterface holds everything shared: weapon pickup and socket attachment, weapon-box collision toggled by anim notifies during a swing, an Attributes component that all damage routes through, and montage playback for attacks, hit reactions and death. AControlledCharacter (player) and AEnemy derive from it and only add what's genuinely different — the player reads input, the enemy runs a state machine. Weapon behaviour is data-driven off an EWeaponType enum that indexes into montage arrays, attach sockets, and hit-sound arrays, so a new weapon class is data, not code.

Trade-off: a fat base class collects responsibilities over time. For a sandbox at this scale that was fine — but a component-based split (a "combatant" component attachable to any actor) would scale better if this grew, and it's how I'd start today.
02 / Directional Reactions

A hit from behind shouldn't play the same as a hit to the face

The problem

Hit reactions and deaths that always play the same animation break the read of a fight — the player can't tell which of two enemies landed the blow, and a back-stab looks identical to a parry-trade. The reaction has to know where the hit came from.

The decision

On every hit, compute the angle between the character's forward vector and the direction to the impact point — dot product for the magnitude, the sign of the cross product's Z for which side — then bucket it into front / back / left / right and play the matching montage section. Death montages use the same angle but pick randomly among several directional variants so repeated kills from the same side still look different.

03 / Enemy State Machine

An explicit C++ state machine that doesn't stutter at the edges

The problem

The enemy cycles through patrolling, chasing, closing to attack range, attacking, and recovering. The naive version — "if within attack radius, attack; else chase" — thrashes: a target hovering right on the attack radius makes the enemy flip between chase and attack every frame, and interruptions (getting hit mid-swing) leave it stuck in a state that no longer makes sense.

The decision

An ordered EEnemyState enum (Patrolling → Alarm → Chasing → Engaged → Attacking → Dead) with a single re-evaluation point. Perception comes from a PawnSensingComponent (sight cone plus hearing). Patrol dwell time and attack cadence are randomized timers, not fixed. The key fix for the thrash is hysteresis: the radius to enter attack range is smaller than the radius to leave it, so once engaged the enemy commits until the target genuinely backs off. Anim-notify callbacks at the end of the attack, hit reaction, and alarm animations are what re-run the decision — the state can't advance until the current animation says it's allowed to.

Trade-off: a hand-written state machine in C++ is more rigid than a Behavior Tree a designer could retune. I chose it deliberately here — the whole project is a C++ exercise — but for anything team-facing this logic belongs in a BT or State Tree.
04 / Group Aggro

One guard spots you, the whole patrol turns

The problem

Enemies that each independently notice the player produce a trickle of one-at-a-time engagements — the player mows down a line of guards who never react to their neighbour dying three metres away. A group needs to alert as a group.

The decision

Enemies register with a shared AEnemyCommander actor. When one sees the player, it freezes and plays an alarm animation; an anim notify at the end of that animation tells the commander, which pushes the player as the combat target to every enemy in its list — the whole group drops into chasing at once. An IsAlreadyInformed() guard means only the first sighting triggers the alarm; after that, newly-spotting enemies just engage directly without replaying the whole ceremony.

Trade-off: the commander is a hand-placed actor with an explicit enemy list rather than a dynamic proximity broadcast. Simpler to reason about and debug, but it means group membership is authored, not emergent — fine for set-piece encounters, limiting for an open patrol sim.
05 / Attacks That Land

Motion warping to kill the whiff

The problem

Root-motion attack animations play at a fixed distance. In a real fight the target is never exactly there — they're a little too far and the swing sails through air, or a little too close and the animation shoves them through the character. Both feel terrible.

The decision

Every tick, if a combat target is within attack range, the character updates two Motion Warping targets: a translation target offset back from the enemy by a set distance so the attacker ends the lunge just short of contact, and a rotation target so the swing actually faces them. When the target leaves range, both warp targets are removed so ordinary locomotion isn't affected. The animation does the rest — the warp just corrects the last bit of spacing.

06 / Where It Would Go Next

The experiment's open threads

What's missing

It's explicitly unfinished. The obvious next systems are the ones a fuller combat loop needs: archery, stealth / backstab damage, a weapon inventory with swapping, weapons degrading with use, hand-to-hand, and throwable weapons.

The direction

Most of these want the base class broken into components first — a combatant component, a weapon-handler component — so archery and hand-to-hand aren't if branches inside one Attack(). The group AI would move to a proper coordinator that assigns roles (flankers, a pusher) instead of just broadcasting a target. Those two refactors unblock most of the list.
